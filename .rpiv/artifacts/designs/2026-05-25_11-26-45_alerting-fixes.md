# Design: Alerting Fixes — Addressing Code Review Findings

## Summary

Five targeted fixes across bifrost (OSS) and bifrost-enterprise addressing code review findings: add `EachRequestLimit` to GovernanceStore for symmetric request-limit alert evaluation; wrap evaluator calls with `Context.WithTimeout` (5s) to prevent blocking the request path; bound RouteStateObserver goroutines with a non-blocking semaphore; fix cooldown-before-send panic safety via defer+recover; and make `decryptString` idempotent via base64 pre-check. The deprecated adapter methods (`EvaluateBudgetAlert`, `EvaluateRateLimitAlert`, `RecordRequest`) were already removed during the `plugins/governance/alerting/` → `core/alerting/` refactor.

## Requirements

- Prevent `UsageAlertEvaluator.OnUsageUpdated` from blocking the request path indefinitely
- Enable request-limit alert evaluation (currently only token limits are iterable)
- Prevent unbounded goroutine accumulation in `OnDirectionStateChanged` / `OnTACOSAnomaly`
- Remove dead code (deprecated `EvaluateBudgetAlert`, `EvaluateRateLimitAlert`, `RecordRequest` on AlertManager)
- Ensure cooldown is not permanently consumed if `sendAlert` panics
- Fix potential double-decrypt in `TableAlertChannel.AfterFind`

## Current State Analysis

### Key Discoveries

- `plugins/governance/store.go:56-60` — `EachRateLimit` only exposes `tokenCurrentUsage`/`tokenMaxLimit`. Request limits (`RequestCurrentUsage`, `RequestMaxLimit`) are not iterable through the GovernanceStore interface.
- `plugins/governance/tracker.go:135,166` — `OnUsageUpdated` runs inline in `UpdateUsage()`. If the evaluator hangs, it blocks all governance-tracked requests. Precedent: `EventBroadcaster` removed after 2 days for the same reason.
- `core/alerting/manager.go:457,476` — `OnDirectionStateChanged` and `OnTACOSAnomaly` fire `go func()` without bound. Under 5s RecomputeMetrics cycle, goroutines can accumulate.
- `core/alerting/manager.go:378` — Cooldown mark (`lastFired[ck] = time.Now()`) is set BEFORE `sendAlert()` completes. If `sendAlert` panics, cooldown is consumed permanently.
- `stores/configstore/tables/alertchannel.go:42-49` — `AfterFind` calls `decryptString(&ac.EncryptedConfig)`. If GORM calls `AfterFind` twice (e.g., explicit call + hook), already-decrypted string is decrypted again.
- `core/alerting/manager.go:627-636` — `EvaluateBudgetAlert()`, `EvaluateRateLimitAlert()`, `RecordRequest()` are public adapter methods matching the removed `AlertEvaluator` interface. Zero callers — `UsageAlertEvaluator` calls private methods directly.

### Precedents & Lessons

- **EventBroadcaster removed after 2 days** (bifrost): Callback patterns in governance mutation paths get reverted to polling. Evaluator must be timeboxed.
- **Logging plugin semaphore pattern** (logging/main.go:182-191): Channel-based semaphore with `select/default` for non-blocking drop — proven pattern for bounding async goroutines.
- **GORM hook pattern** (all table files): BeforeSave/AfterFind always serializes from `gorm:"-"` field to DB column. `decryptString` on already-decrypted data should be safe if the function checks its input format.

## Decisions

### Decision 1: Evaluator Timeout Strategy

- **Ambiguity**: Should the evaluator be wrapped with a context timeout or dispatched to an async goroutine pool?
- **Explored**: (A) `Context.WithTimeout` wrapper — keeps evaluator inline, simple, 5s hard timeout. Matches MCP toolmanager.go:672 and gRPC dial timeout at cluster/grpc/pool.go:196. (B) Semaphore-guarded async goroutine — fully non-blocking but adds goroutine lifecycle management. Matches logging/main.go:182-191.
- **Decision**: `Context.WithTimeout` wrapper (5s). The evaluator is lightweight (iterating in-memory maps + calling private methods). Timeout is a safety net, not a throughput concern. Simpler to implement and reason about.

### Decision 2: Goroutine Bounding Strategy

- **Ambiguity**: How to prevent goroutine leaks in RouteStateObserver handlers?
- **Explored**: (A) Non-blocking semaphore (cap=100) — proven pattern from logging/main.go:182. Drops excess goroutines with a warning log. (B) Fixed-size worker pool — more robust but significantly more complex (WasmWorkerPool is 209 lines).
- **Decision**: Non-blocking semaphore (cap=100). Matches the logging plugin pattern exactly. Simple, bounded, graceful degradation.

### Decision 3: Request Limit Interface Design

- **Ambiguity**: Should request limits get their own method or extend the existing `EachRateLimit` callback?
- **Explored**: (A) `EachRequestLimit` — new symmetric method. Clean separation, no backward compatibility issue. (B) Extend `EachRateLimit` callback signature — fewer surface changes but breaks existing callers.
- **Decision**: New `EachRequestLimit` method on `GovernanceStore`. Clean API, no breaking changes.

### Decision 4: Cooldown Safety

- **Ambiguity**: Keep cooldown before send or move after?
- **Explored**: (A) Move after send + defer — set cooldown only after successful send, defer sets it even on panic. Prevents permanent consumption. (B) Keep before-send with panic recovery that rolls back cooldown — more complex.
- **Decision**: Move after send + defer with panic recovery. Simpler, same safety properties.

### Decision 5: Double-Decrypt Fix

- **Ambiguity**: Flag-based guard or idempotent decrypt?
- **Explored**: (A) Make `decryptString` idempotent — check if input is already decrypted (not base64-encoded/garbled). Matches existing GORM pattern where BeforeSave always serializes from scratch. (B) Add `isDecrypted` bool flag to struct — explicit but adds persistent state.
- **Decision**: Make `decryptString` idempotent. Simpler, no struct changes, matches codebase conventions.

// EachRequestLimit calls fn for every rate limit that has a request-limit configured.
// Used by the enterprise alerting engine to evaluate request-limit threshold rules.

Implementation on LocalGovernanceStore:

```go
// EachRequestLimit calls fn for every rate limit that has a request-limit configured.
func (gs *LocalGovernanceStore) EachRequestLimit(fn func(rateLimitID string, requestCurrentUsage, requestMaxLimit int64)) {
	gs.rateLimits.Range(func(key, value any) bool {
		rl, ok := value.(*configstoreTables.TableRateLimit)
		if ok && rl != nil && rl.RequestMaxLimit != nil {
			fn(key.(string), rl.RequestCurrentUsage, *rl.RequestMaxLimit)
		}
		return true
	})
}
```

### stores/configstore/tables/encryption.go — MODIFY

```go
// decryptString — idempotent (checks base64 validity before decrypting)
func decryptString(value *string) error {
    if value == nil || *value == "" {
        return nil
    }
    // If not valid base64, it's already plaintext — skip.
    if _, err := base64.StdEncoding.DecodeString(*value); err != nil {
        return nil
    }
    decrypted, err := encrypt.Decrypt(*value)
    if err != nil {
        return err
    }
    *value = decrypted
    return nil
}
```

## What This Design Doesn't Cover (Intentional Gaps)

1. **No latency field in UsageUpdate** — The enterprise `recordRequest` accepts a `latency` parameter but the OSS `UsageUpdate` struct doesn't carry one. Latency anomalies are detected by the TACOS observer path (`OnTACOSAnomaly` → `RecordLatencyAnomaly`), not via usage-based rolling windows. Documented in `usagetracker.go`.

2. **No full load-balancer-to-observer integration test** — The observer handler is tested at the unit level in `observer_integration_test.go` and `observer_test.go`. The wiring in `server.go:2625` and trigger in `tracker.go:556-562` are verified by reading the code but not by an automated test that runs through the full LB `RecomputeMetrics` path. Acceptable because the handler unit tests prove correctness.

3. **No e2e test for the full alert trigger chain** — No automated test makes a real API request, waits for the sweeper, and checks alert history. The manual smoke test is documented in `ALERTING_ONBOARDING.md`. Acceptable because waiting 60s for the sweeper is impractical in CI.

## Performance Considerations

- `EachRequestLimit` iterates the same `sync.Map` as `EachRateLimit` — negligible overhead (one extra Range pass per usage update)
- Context timeout is not freed per-call — `context.WithTimeout` allocates; acceptable for the rate of usage updates
- Non-blocking semaphore (cap=100) bounds worst-case goroutine count to 100 even under sustained 5s cycles

## Migration Notes

- `EachRequestLimit` is additive — no existing callers to migrate
- Removing deprecated methods `EvaluateBudgetAlert`, `EvaluateRateLimitAlert`, `RecordRequest` — must verify zero callers before removal. Grep confirms all three are dead code.
